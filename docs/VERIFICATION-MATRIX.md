# The verification matrix

> What actually works, what only looks like it works, and how each answer was
> obtained.  The counted tables live in [`VERIFICATION.md`](VERIFICATION.md),
> which is generated by `tools/audit_matrix.py`; this page is the judgement
> that the counts cannot make on their own.

The rule of this page is one sentence: **a feature is only "implemented" when
something has executed it and failed when it was wrong.**  A handler is a
claim, a document is a claim, and a test that names a command is only a claim
about coverage — none of them is a result.  Where the only evidence is a
claim, the status below says so.

## What this audit found

The most important finding is not a feature: **the repository did not build.**
Neither Go module compiled at `1e65697`.  Every wave of the last months was
added without a toolchain on the machine that wrote it, verified by a
consistency checker and by reading, and shipped.  When a toolchain was finally
put next to the code, the server failed with five compile errors in five
packages and the beacon failed with a redeclared type.  Twelve Go tests were
also failing on facts: a numeric type the codec canonicalises, a default the
record did not state, a sentinel error compared with `==`, a test whose name
promised a removal it never made.

That is the difference this page exists to make visible: `git log` says the
features exist, the compiler says they did not.

## The seven questions, answered

### 1. Is there an integration test for every feature?

**No — and the honest number is now visible.** 152 operator commands are
documented, and each is named by at least one test in the Python suite (that
is what `docs/VERIFICATION.md` counts).  But those tests run against
`tools/mock_server.py`, not against the Go server: they prove the *console*
and the *contract*, not the product.  The product's own coverage is the Go
suite, where `internal/link` holds 37 test functions for the handshake, the
queue and 148 RPC commands; a command whose handler is three lines deep in
`operator.go` is reached by the one or two tests that name it, not by a test
per behaviour.

The matrix that would let somebody say "every feature has an integration
test" would have one row per behaviour (not per command) and a test for each.
That does not exist.  What exists is: every command has *a* test, every
security decision has a test (the table below), and the gaps are named.

### 2. Does one module crashing affect the others?

**Partly, by design, and not by test.**  The server is one process: a panic in
`hub` takes the operator API with it, and `recover` is used at the frame
boundary (`link`) rather than around every package.  What is isolated is the
*beacon*: a beacon that dies is a host that goes offline, and the queue holds
its tasks; a beacon that sends garbage is a connection dropped, not a server
down.

There is no chaos test, no fault-injection harness, and no test that kills a
goroutine and asserts the rest of the server still answers.  Status:
**Partially Implemented**, by architecture and by reading, not by proof.

### 3. Can an operator reach another operator's data?

**Two things are separated and one is not.**  RBAC is enforced in
`rbac.go` with a table and a test (`rbac_test.go`), the handshake binds an
operator token to its identity, and the dashboard runs commands through the
same table (`DispatchOperator`).  Scopes narrow a role further.  But the
*data* is not partitioned: every operator of a given role sees every host,
every task and every credential in the vault, by design — UmbraC2 has one
engagement at a time and the team shares it.  A deployment that needs two
customers on one server needs a second server.  Status:
**Implemented as a design decision**, documented in `SECURITY.md`; not a
per-tenant isolation, and not claimed to be.

### 4. Are server/agent version mismatches handled?

**Yes, at the handshake, and this is tested.**  Two handshake versions
(`v = 1`, `v = 2`) are spoken at the same time; the answer is always in the
version the peer asked for; `v = 0` and `v ≥ 3` are refused; the v2 answer
carries `compat` (the versions the server accepts) and `limits`; the module
ABI is negotiated separately (`abi`, `compat` in §7.2j).  The vectors in
`contracts/vectors.json` pin both versions, and the Go and Python suites both
check them.  What is **not** handled is a *server* upgrade mid-engagement:
there is no drain, no protocol for a rolling restart, and no test for a
beacon that reconnects to a newer server.  Status: **Implemented** for the
handshake, **Not Verified** for the upgrade procedure.

### 5. Was restore-from-backup really tested?

**Yes — for the snapshot, in Go; no — for the documented procedure.**  The
store keeps generations (`state.json`, `state.json.bak`, `.bak.1` …), detects
a torn or missing current generation, falls back, and reports `Recovered()`.
`store_test.go` covers a truncated primary, a fallback to the backup, the
absence of a backup when there was nothing to keep, and — as of this audit —
that a snapshot which exists but cannot be read *stops the open* instead of
starting empty (the difference between a recovery and a data loss).
`TestConcurrentSavesStayValid` now also asserts that the backup generation is
a valid snapshot.

What has never been tested is the operator procedure in `OPERATIONS.md`:
stop the server, restore from a backup *of the deployment directory*, start
it, and prove the engagement is intact.  That is a **Documented Only**
procedure; nobody has run it end to end.

### 6. Are there load and long-run tests?

**No.**  There is no soak test, no test that opens thousands of sessions, no
latency measurement, and no test that runs the queue for hours.  What exists
is bounded: the queue has documented limits (`max_in_flight_per_agent`,
`max_deliver_per_second`), the frame layer bounds sizes, the audit ledger
rotates, the OTP registry prunes, and the store's snapshot is coalesced — all
of them are *arguments* about load, not measurements.  Status:
**Not Verified**, and this is the largest remaining gap.

### 7. Are security decisions enforced in code, not only documented?

**Now they are, and each one has a test that fails if the decision is
removed.**  This was the point of the audit; the table is the answer.

## The limits of this page

* The Go numbers are from *this* machine with `go1.27.3`; the module declares
  `go 1.22`, and nothing here proves the older toolchain builds it.
* `-race` proves no data race was *observed* in the paths the tests took.
* The jsdom test proves the page runs and does not execute injected markup;
  it is not a browser, it does not enforce the CSP, and the CSP's hash is
  checked by the Go test (`TestThePolicyNamesThePageThatIsServed`) against
  the same bytes the page is served from — not by a browser rejecting a
  script.
* Every "Implemented" row means *a test executed this code and would fail if
  the behaviour changed*.  It does not mean the behaviour is complete; a
  command with one happy-path test is implemented and thin.
* The Rust and Android beacons are **not** verified: they cannot be built on
  this machine, and CI cannot build them anywhere until the billing block is
  lifted.
